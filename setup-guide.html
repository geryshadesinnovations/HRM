End-to-End Setup & Run Guide

A complete, copy-paste runbook to get the HRMS SaaS platform fully running — first on your local machine, then on a production VPS. Every tool, every command, every environment value, and a smoke test to prove it works. No prior knowledge of the project assumed.

What is "the app"?
The platform has two parts, both in this repo: a Laravel 12 REST API backend (backend/ — multi-tenancy, auth, subscriptions, Employees, Attendance, Leave, Payroll, Billing) and a Next.js web frontend (frontend/ — login, dashboards, and screens for every module). The frontend is a browser SPA that talks to the API. This guide gets both running: the API on :8000 and the web app on :3000.
Which path should I pick?
Docker is the fastest and most reliable — it installs PostgreSQL, Redis, PHP, the queue worker and scheduler for you. Choose native only if you cannot use Docker or want each service installed directly on the host. Both paths are fully documented below.

2. Path A — Run on localhost with Docker RECOMMENDED

This brings up six containers: app (PHP-FPM), nginx (web server on port 8000), postgres, redis, horizon (queue worker), and scheduler. You only need Docker and Git installed.

Step 1 — Install Docker

Windows / macOS Install Docker Desktop and start it. Ubuntu install Docker Engine + Compose plugin:

sudo apt update && sudo apt install -y docker.io docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker $USER     # then log out/in so you can run docker without sudo
docker --version && docker compose version    # verify

Step 2 — Clone the repository

git clone https://github.com/geryshadesinnovations/HRM.git
cd HRM

Step 3 — Create the environment file

cp backend/.env.example backend/.env
CRITICAL for Docker: fix the host names
The example file points the database and Redis at 127.0.0.1, which is correct for a native install but wrong inside Docker — there, services reach each other by their compose service name. Edit backend/.env and set: 
DB_HOST=postgres
REDIS_HOST=redis
Leave DB_DATABASE=hrms, DB_USERNAME=hrms, DB_PASSWORD=secret as-is (they match the Postgres container defaults).

Step 4 — Set a JWT secret (required, or login/tokens fail)

The auth system signs tokens with JWT_SECRET. Generate one and write it into backend/.env:

# macOS/Linux: generate a 64-char secret and set it in .env
SECRET=$(openssl rand -hex 32)
sed -i.bak "s/^JWT_SECRET=.*/JWT_SECRET=$SECRET/" backend/.env

# (Windows PowerShell alternative)
# $s = -join ((48..57)+(97..102) | Get-Random -Count 64 | % {[char]$_})
# then paste it after JWT_SECRET= in backend/.env

Step 5 — Build and start the stack

docker compose -f infra/docker-compose.yml up -d --build

Wait until docker compose -f infra/docker-compose.yml ps shows the containers up (Postgres has a healthcheck the app waits on).

Step 6 — Install dependencies, generate the app key, migrate & seed

Why this runs inside the container
The compose file bind-mounts backend/ into the container, which hides the vendor folder baked into the image. So run Composer once inside the running container to populate backend/vendor, then set the key and build the database.
cd infra
docker compose exec app composer install
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate --seed
docker compose restart horizon scheduler   # pick up the freshly installed vendor
cd ..

The --seed step creates the canonical data: 7 modules, 3 plans (Starter/Growth/Enterprise), 5 roles with ~30 permissions, and the Super Admin account.

Step 7 — It's running

  • Web app (UI): http://localhost:3000 — open this and log in.
  • API base URL: http://localhost:8000
  • Health check: open http://localhost:8000/up → should say the app is up.
  • Super Admin login: superadmin@hrms.test / password (override via SUPER_ADMIN_EMAIL/SUPER_ADMIN_PASSWORD before seeding).

The frontend container builds on first up (it may take a minute). Then open http://localhost:3000 and click Start a free trial. Or jump to §4 to drive the product over HTTP.

Handy Docker commands

cd infra
docker compose -f docker-compose.yml logs -f app      # tail API logs
docker compose -f docker-compose.yml ps               # container status
docker compose -f docker-compose.yml exec app php artisan tinker   # REPL
docker compose -f docker-compose.yml exec app php artisan test     # run tests
docker compose -f docker-compose.yml down             # stop (keeps data volume)
docker compose -f docker-compose.yml down -v          # stop AND delete the database

3. Path B — Run on localhost with a native install

Here you install PHP, Composer, PostgreSQL, Redis, Node, and Git directly on your machine. Pick your OS below, then continue to §3.4 which is the same for everyone.

3.4 Configure, migrate & run (all OSes)

Run everything from the backend/ directory.

git clone https://github.com/geryshadesinnovations/HRM.git
cd HRM/backend

# 1. PHP dependencies
composer install

# 2. Environment file
cp .env.example .env          # native install: keep DB_HOST=127.0.0.1 and REDIS_HOST=127.0.0.1

# 3. Application key
php artisan key:generate

# 4. JWT secret (REQUIRED)
SECRET=$(openssl rand -hex 32)
sed -i.bak "s/^JWT_SECRET=.*/JWT_SECRET=$SECRET/" .env     # macOS/Linux/WSL

# 5. Create the database + user in PostgreSQL
sudo -u postgres psql -c "CREATE USER hrms WITH PASSWORD 'secret';"
sudo -u postgres psql -c "CREATE DATABASE hrms OWNER hrms;"
#   (.env already has DB_DATABASE=hrms / DB_USERNAME=hrms / DB_PASSWORD=secret)

# 6. Build the schema and seed reference data (modules, plans, roles, super admin)
php artisan migrate --seed

# 7. Build front-end assets (optional for API-only use)
npm install
npm run build

# 8. Start the API
php artisan serve            # serves http://localhost:8000

Start the background worker & scheduler (separate terminals)

For the platform to be fully functional (queued jobs + the subscription lifecycle sweep), run these alongside php artisan serve:

# Terminal 2 — process queued jobs
php artisan queue:work --tries=3 --timeout=120

# Terminal 3 — run scheduled tasks (e.g. subscriptions:sweep, hourly)
php artisan schedule:work
One-command dev mode
The repo ships a Composer script that runs the server, queue, logs, and Vite together: 
composer dev
(Requires Node, since it uses npx concurrently.)

Now continue to §4 to confirm everything works.

3.5 Run the web UI (Next.js frontend)

The frontend is the browser app your users log into. It lives in frontend/ and talks to the API you started above.

Docker users: it's already running
The Docker stack (§2) includes a frontend container — the web app is already at http://localhost:3000. Skip to §4 (or just open it in a browser and log in). The steps below are for a native/local Node setup.
# In a new terminal, from the repo root:
cd HRM/frontend

# 1. Tell the UI where the API is
cp .env.example .env.local
#   .env.local should contain:  NEXT_PUBLIC_API_URL=http://localhost:8000

# 2. Install dependencies
npm install

# 3a. Development mode (hot reload) — recommended while developing
npm run dev          # opens http://localhost:3000

# 3b. OR production build + serve
npm run build
npm run start        # serves http://localhost:3000

Open http://localhost:3000. You'll see the login screen. Click "Start a free trial" to register a company (or log in with the super admin superadmin@hrms.test / password). The sidebar shows Employees, Attendance, Leave, Payroll and Billing — each gated by the company's plan and the user's role.

CORS
The API already allows browser calls (a config/cors.php ships with the backend, defaulting to allow all origins for Bearer-token auth). In production, set CORS_ALLOWED_ORIGINS=https://app.yourdomain.com in the backend .env to restrict it.

4. Verify it actually works (end-to-end smoke test)

Easiest check: use the web app
Open http://localhost:3000, click Start a free trial, register a company on the Growth plan, and you'll land on the dashboard with Employees / Attendance / Leave / Payroll / Billing in the sidebar. Add an employee, mark attendance, run payroll — if those screens work, the whole stack works. The curl flow below is the same thing at the API level (useful for CI or headless checks).

This walks the full product over HTTP: health → create a company → log in → call authenticated and subscription-gated endpoints. It works identically for the Docker and native setups (same http://localhost:8000). Install jq for pretty JSON, or drop the | jq parts.

4.1 Health check

curl -i http://localhost:8000/up
# Expect: HTTP/1.1 200 OK

4.2 Register a company (creates company + admin user + trial subscription)

We pick the growth plan so Attendance, Leave and Payroll are all licensed.

curl -s -X POST http://localhost:8000/api/v1/auth/register-company \
  -H "Content-Type: application/json" \
  -d '{
    "company_name": "Acme Pvt Ltd",
    "admin_name": "Asha Rao",
    "email": "asha@acme.test",
    "password": "secret123",
    "password_confirmation": "secret123",
    "plan_code": "growth"
  }' | jq

# Response (201) contains data.company, data.user, and data.tokens.{access_token, refresh_token}

4.3 Log in and capture the access token

TOKEN=$(curl -s -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"asha@acme.test","password":"secret123"}' \
  | jq -r '.data.tokens.access_token')

echo "$TOKEN"     # should print a long JWT

4.4 Call authenticated endpoints

# Who am I? (profile + roles + permissions)
curl -s http://localhost:8000/api/v1/me -H "Authorization: Bearer $TOKEN" | jq

# What is this company entitled to? (status, modules, features, seats)
curl -s http://localhost:8000/api/v1/me/entitlements -H "Authorization: Bearer $TOKEN" | jq

# Available plans
curl -s http://localhost:8000/api/v1/plans -H "Authorization: Bearer $TOKEN" | jq

4.5 Exercise the business modules

# Create an employee (subject to the plan's seat limit)
EMP=$(curl -s -X POST http://localhost:8000/api/v1/employees \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"employee_code":"E1","first_name":"Ravi","last_name":"Kumar","status":"active"}')
echo "$EMP" | jq
EMP_UUID=$(echo "$EMP" | jq -r '.data.uuid')

# List employees
curl -s http://localhost:8000/api/v1/employees -H "Authorization: Bearer $TOKEN" | jq

# Mark attendance for that employee (module:attendance is licensed on growth)
curl -s -X POST http://localhost:8000/api/v1/attendance/mark \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d "{\"employee\":\"$EMP_UUID\",\"work_date\":\"2026-06-25\",\"status\":\"present\"}" | jq

# Create a leave type, then a payroll component (module:leave / module:payroll)
curl -s -X POST http://localhost:8000/api/v1/leave/types \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"code":"casual","name":"Casual Leave","is_paid":true,"annual_quota":12}' | jq

curl -s -X POST http://localhost:8000/api/v1/payroll/components \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"code":"BASIC","name":"Basic","type":"earning"}' | jq
If all of the above returned JSON (not errors)
The platform is fully functional: multi-tenancy, JWT auth, RBAC, the subscription gate, and the HR/Attendance/Leave/Payroll modules are all live and wired to the database. A web or mobile client now simply calls these same endpoints with the Authorization: Bearer header.

6. Deploy to a VPS — overview & sizing

A VPS (e.g. DigitalOcean, Hetzner, Linode, AWS Lightsail/EC2) is a Linux server you rent. We target Ubuntu 22.04/24.04 LTS. As with localhost there are two paths:

  • Path A — Docker Compose on the VPS (§8): fastest; the same stack as local, with a host Nginx + SSL in front. Best for a single server.
  • Path B — Native production (§9): each service installed on the host, workers under Supervisor. Most control; standard for scaling later.

Recommended sizing

ScalevCPURAMDiskNotes
Pilot / ≤50 companies24 GB40 GB SSDAll-in-one (Docker path is ideal)
Growing48–16 GB100 GB SSDConsider managed Postgres/Redis
Largeapp: N×24 GB/nodemanaged DBLoad balancer + multiple stateless app nodes

First 5 minutes on a fresh server (do this for either path)

# SSH in as root (or a sudo user) using the IP your provider gave you
ssh root@YOUR_SERVER_IP

# Patch the OS
apt update && apt upgrade -y

# Create a non-root deploy user (safer than working as root)
adduser deploy && usermod -aG sudo deploy

# Basic firewall: allow SSH + web
apt install -y ufw
ufw allow OpenSSH
ufw allow 80
ufw allow 443
ufw --force enable

7. Domain & DNS

Point a domain at the server before requesting SSL certificates.

  1. In your DNS provider, create an A record: api.yourdomain.com → YOUR_SERVER_IP.
  2. Wait for propagation (usually minutes). Verify: dig +short api.yourdomain.com returns your IP.

This guide uses api.yourdomain.com as the API host throughout — replace it with yours.

8. Path A — Docker Compose on the VPS

Step 1 — Install Docker

curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER && newgrp docker
docker --version && docker compose version

The stack now serves on 127.0.0.1:8000 (compose maps nginx to host port 8000). We put a host Nginx + SSL in front of it next (§11). The horizon and scheduler containers already run the queue worker and scheduled tasks for you.

Step 6 — Nginx site (HTTP first; SSL added in §11)

sudo tee /etc/nginx/sites-available/hrms >/dev/null <<'NGINX'
server {
    listen 80;
    server_name api.yourdomain.com;
    root /var/www/HRM/backend/public;     # Laravel's public dir is the web root
    index index.php;
    client_max_body_size 25m;

    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;

        fastcgi_index index.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
    }
    location ~ /\.(?!well-known).* { deny all; }
}
NGINX

sudo rm -f /etc/nginx/sites-enabled/default

Visit http://api.yourdomain.com/up — it should return 200. Continue to §9.5–§11.

9.5 Deploy the frontend (web UI)

Serve the Next.js app on its own host, e.g. app.yourdomain.com, pointed at the public API URL.

Build-time API URL
NEXT_PUBLIC_API_URL is baked into the browser bundle at build time. Set it to your public API URL (e.g. https://api.yourdomain.com) before building — not localhost.

Docker path

The compose stack already includes a frontend service on port 3000. Build it with the public API URL and reverse-proxy your app domain to it:

# build the frontend image with the real API URL, then (re)start it
cd /var/www/HRM
NEXT_PUBLIC_API_URL=https://api.yourdomain.com \
  docker compose -f infra/docker-compose.yml up -d --build frontend

# host Nginx vhost: app.yourdomain.com → the frontend container on :3000
sudo tee /etc/nginx/sites-available/hrms-app >/dev/null <<'NGINX'
server {
    listen 80;
    server_name app.yourdomain.com;
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
NGINX
sudo ln -sf /etc/nginx/sites-available/hrms-app /etc/nginx/sites-enabled/hrms-app
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d app.yourdomain.com

Native path

cd /var/www/HRM/frontend
npm ci
echo "NEXT_PUBLIC_API_URL=https://api.yourdomain.com" > .env.local
npm run build
# run it persistently (example with pm2):
sudo npm i -g pm2
pm2 start "npm run start" --name hrms-frontend
pm2 save && pm2 startup     # survive reboots
# then add an Nginx vhost for app.yourdomain.com → 127.0.0.1:3000 (as above) + certbot
Lock down CORS
In the backend .env, set CORS_ALLOWED_ORIGINS=https://app.yourdomain.com so only your frontend can call the API from a browser.

10. Queue worker + scheduler (always-on)

The platform needs two background processes running permanently: the queue worker (processes jobs) and the scheduler (runs subscriptions:sweep and future timed tasks). With the Docker path these are already the horizon and scheduler containers — skip this section. For the native path, use Supervisor + cron.

Queue worker via Supervisor

sudo tee /etc/supervisor/conf.d/hrms-worker.conf >/dev/null <<'CONF'
[program:hrms-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/HRM/backend/artisan queue:work redis --sleep=3 --tries=3 --timeout=120
autostart=true
autorestart=true
user=www-data
numprocs=2
redirect_stderr=true
stdout_logfile=/var/log/hrms-worker.log
stopwaitsecs=3600
CONF

sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl status        # should show hrms-worker:* RUNNING

Scheduler via cron

# Run Laravel's scheduler every minute (it internally decides what's due).
sudo crontab -u www-data -e
# add this single line:
* * * * * cd /var/www/HRM/backend && php artisan schedule:run >> /dev/null 2>&1

Verify the sweep command is registered: php artisan list | grep subscriptions:sweep.

11. HTTPS / SSL (free, via Let's Encrypt)

Never run an auth API over plain HTTP in production — Bearer tokens would be exposed.

Native path

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d api.yourdomain.com
# Certbot edits your Nginx site to add SSL and sets up auto-renewal.
sudo certbot renew --dry-run     # confirm renewal works

Docker path — host Nginx reverse proxy + SSL

Put a host Nginx in front of the compose stack (which listens on 127.0.0.1:8000):

sudo apt install -y nginx certbot python3-certbot-nginx

sudo tee /etc/nginx/sites-available/hrms >/dev/null <<'NGINX'
server {
    listen 80;
    server_name api.yourdomain.com;
    client_max_body_size 25m;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
NGINX

sudo ln -sf /etc/nginx/sites-available/hrms /etc/nginx/sites-enabled/hrms
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d api.yourdomain.com
Tell Laravel it's behind HTTPS
Set APP_URL=https://api.yourdomain.com so generated URLs use HTTPS. The reverse proxy passes X-Forwarded-Proto which Laravel's trusted-proxy handling respects.

# Frontend / CORS — restrict browser origins to your web app in production

# (frontend build-time var, set in frontend/.env.local or the Docker build arg)
# NEXT_PUBLIC_API_URL=https://api.yourdomain.com
Security must-dos
  • Change the default super-admin password (password) — set SUPER_ADMIN_PASSWORD before seeding, or change it after.
  • Use a unique, random JWT_SECRET and DB_PASSWORD per environment. Never commit .env.
  • Keep APP_DEBUG=false. Keep Postgres (5432) and Redis (6379) bound to localhost / private network — only 80/443 should be public.
  • Real payment gateways (Razorpay/Cashfree/PayU) are not yet implemented — the platform falls back to the manual/offline payment adapter until those are added.

13. Go-live checklist

  • ☐ DNS A record resolves to the server (dig +short api.yourdomain.com).
  • ☐ https://api.yourdomain.com/up returns 200 over HTTPS (valid cert).
  • ☐ APP_ENV=production, APP_DEBUG=false, strong JWT_SECRET & DB_PASSWORD set.
  • ☐ php artisan migrate --force --seed ran (plans, modules, roles, super admin exist).
  • ☐ Super-admin password changed from the default.
  • ☐ Queue worker running (Supervisor or horizon container) and scheduler active (cron or scheduler container).
  • ☐ Config/route caches built (config:cache, route:cache).
  • ☐ storage/ + bootstrap/cache owned by www-data.
  • ☐ Firewall allows only 22/80/443; DB & Redis are private.
  • ☐ The §4 smoke test passes against the live domain.
  • ☐ Frontend built with NEXT_PUBLIC_API_URL=https://api.yourdomain.com and reachable at https://app.yourdomain.com; CORS_ALLOWED_ORIGINS set to it.
  • ☐ A database backup job is scheduled (§15).

14. Updating & redeploying a new version

Native

cd /var/www/HRM
git pull origin main          # or your release branch
cd backend
composer install --no-dev --optimize-autoloader
php artisan migrate --force
php artisan config:cache && php artisan route:cache && php artisan event:cache
sudo supervisorctl restart hrms-worker:*   # restart workers to load new code
sudo systemctl reload php8.4-fpm

Docker

cd /var/www/HRM
git pull
docker compose -f infra/docker-compose.yml up -d --build
cd infra
docker compose exec app composer install --no-dev --optimize-autoloader
docker compose exec app php artisan migrate --force
docker compose exec app php artisan config:cache
docker compose restart app horizon scheduler
# rebuild the frontend if its code or NEXT_PUBLIC_API_URL changed:
NEXT_PUBLIC_API_URL=https://api.yourdomain.com docker compose -f ../infra/docker-compose.yml up -d --build frontend
Zero-ish downtime
Migrations in this project are additive. For risky schema changes use the expand→migrate→contract pattern and never edit a migration that has already shipped — always add a new one.

15. Backups & ongoing operations

Daily database backup (native)

# Add to www-data crontab:
0 2 * * * pg_dump -U hrms hrms | gzip > /var/backups/hrms-$(date +\%F).sql.gz

Daily database backup (Docker)

0 2 * * * cd /var/www/HRM/infra && docker compose exec -T postgres \
  pg_dump -U hrms hrms | gzip > /var/backups/hrms-$(date +\%F).sql.gz

Restore

# native
gunzip -c /var/backups/hrms-2026-06-25.sql.gz | psql -U hrms hrms
# docker
gunzip -c /var/backups/hrms-2026-06-25.sql.gz | docker compose exec -T postgres psql -U hrms hrms

Where to look when something's wrong

  • App logs: backend/storage/logs/laravel.log (native) · docker compose logs -f app (Docker).
  • Queue health: sudo supervisorctl status · failed jobs in the failed_jobs table (php artisan queue:failed).
  • Web/proxy: /var/log/nginx/error.log; PHP-FPM: /var/log/php8.4-fpm.log.
  • Quick env sanity: php artisan about.
