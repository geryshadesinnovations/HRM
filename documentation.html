What this means for a new owner
The hard architectural decisions — tenant isolation that cannot be bypassed by accident, an entitlement engine with zero hardcoded plan logic, clean service layering — are in place, every business module is built on top of them and covered by tests, and a Next.js web UI drives the whole thing in the browser. The product runs end-to-end. Remaining work is production polish: real payment-gateway adapters, report exports, notifications, and MFA.

1. Project understanding (in business language)

What the platform is. A commercial HRMS (Human Resource Management System) sold as SaaS. Many separate companies ("tenants") sign up and use the same software over the internet. Each company manages its own employees, attendance, leave and payroll. Every company's data is walled off from every other company's data.

Why it exists / problems it solves. Small and mid-sized companies normally juggle HR across spreadsheets, WhatsApp messages, and manual salary calculations. This platform replaces that with one system where attendance, leave, and payroll connect automatically — and the vendor (you) earns recurring monthly revenue per company.

SaaS business model

Companies pay a recurring fee. Price = a base plan (which includes a number of employee "seats") + extra seats + optional module add-ons.

Subscriptions

Each company has exactly one live subscription tied to a plan. It moves through states: trial → active → grace → expired/suspended/cancelled. Access is gated by state; data is never deleted.

Modules

Capabilities (Attendance, Payroll, Leave…) are database records, not hardcoded. A plan grants a set of modules. Selling a new module needs no redeploy.

Billing PLANNED

Designed as a gateway-agnostic layer (Razorpay/Cashfree/PayU) driven by webhooks, with GST-aware invoices. Currently configuration only.

Attendance PLANNED

HR-marked or employee self check-in/out, working hours, overtime. Module is sellable today; logic lands in Phase 3.

Payroll PLANNED

Salary structures → monthly payroll runs → payslips, consuming attendance/leave when licensed.

Multi-tenancy

One database, one schema. Every business row carries a company_id. A global query filter makes cross-company access impossible by default.

2. Technical architecture

The backend is a Laravel 12 REST API. It is layered so dependencies only point one direction, and every cross-cutting concern (tenancy, entitlements, auth) lives in a dedicated Platform namespace. The intended frontend is a Next.js SPA (planned); today the API is the whole product.

2.2 Request flow: from browser to database

This is the exact lifecycle of an authenticated, tenant-scoped, subscription-gated request, using the real POST /api/v1/payroll/runs route as the example. Every step below is wired and test-covered today.

1. Client sends  POST /api/v1/payroll/runs   with  Authorization: Bearer <access>

2. auth:api guard  (App\Platform\Auth\JwtGuard)
   • reads the Bearer token, JwtService::decode() verifies signature + "typ":"access"
   • loads the User by the token "sub" claim → request->user()

3. tenant middleware  (ResolveTenant)
   • reads user->company_id → TenantContext::setCompanyId()
   • Super Admin (company_id = null) passes through tenant-less

4. permission:payroll.run.execute  (Spatie PermissionMiddleware)
   • checks the user's roles grant the permission, else 403 FORBIDDEN

5. module:payroll  (EnsureModuleAccess)
   • FeatureAccessService->assert('module:payroll')
   • SubscriptionEngine resolves entitlement (cached in Redis)
   • if plan lacks payroll OR status is blocked → 403 MODULE_NOT_LICENSED

6. Controller → Service
   • FormRequest validates body; Service runs inside DB::transaction
   • Every tenant-aware Model query auto-adds WHERE company_id = <current>

7. Response: ApiResponse::success(...) → { "data": {...}, "meta": {...} }
Two independent gates on every protected route
RBAC answers "is this user allowed to do this?" and Subscription answers "did this company pay for this?". Both must pass. They are separate middleware so they can be reasoned about and tested independently.

Indexing & performance strategy

  • Lead every tenant index with company_id — it is in almost every WHERE clause.
  • Composite indexes match access patterns: employees(company_id,status), subscriptions(status,current_period_end) (drives the daily expiry sweep), refresh_tokens(user_id,revoked_at).
  • Money as BIGINT minor units avoids float rounding bugs in payroll/billing.
  • Planned: high-volume append tables (attendance_records, audit_logs, notifications) are range-partitioned by month so old partitions can be archived and indexes stay small.

4.1 Tenant isolation strategy — the most important invariant

Strategy: single database, shared schema, row-level isolation by company_id. Chosen over database-per-tenant because 10,000+ tenants on one Postgres cluster is operationally sane and makes platform analytics simple. Isolation is enforced in three layers:

  1. Resolution — ResolveTenant middleware reads user->company_id into TenantContext.
  2. Auto-scope & auto-fill — the BelongsToTenant trait adds TenantScope (auto WHERE company_id=? on reads) and auto-fills company_id on insert. Developers cannot forget the filter.
  3. Fail-closed — if there is no tenant and no explicit bypass(), the scope adds WHERE 1=0, returning nothing rather than leaking everything.
Proven by tests
tests/Feature/TenantIsolationTest.php seeds two companies and asserts: (a) each only sees its own rows, (b) company_id is auto-filled on create, and (c) queries with no tenant return zero rows. This runs in CI on every push.
// Any tenant-aware model query is automatically scoped:
Employee::count();   // SELECT count(*) FROM employees WHERE company_id = <current>

// Platform/super-admin code opts out explicitly:
$tenant->bypass(fn () => Subscription::where('company_id', $id)->first());

5. Subscription engine BUILT

The spine of the platform. Every module/feature/seat decision flows through one engine, and there is no hardcoded plan logic anywhere — entitlements are computed from database records.

Core concepts

ConceptMeaningCode
ModuleA sellable capability. Dynamic DB record.Models/Module.php
FeatureA flag/limit within a module (payroll.bulk, employees.max).Models/Feature.php
PlanPriced bundle of modules + feature values + seat economics.Models/Plan.php
SubscriptionA company's live plan instance with status, period, seats, overrides.Models/Subscription.php
EntitlementThe resolved set of modules + feature values for a company right now.Services/Entitlement.php

How an entitlement is resolved

Entitlement(company) =
    Plan.modules  ∪  Plan.features          (base bundle from plan_module / plan_feature)
    ⊕ Subscription.overrides                (per-tenant add: {modules:{add,remove}, features:{code:value}})
    ⊗ SubscriptionStatus gate               (trial/active/grace ⇒ access; expired/suspended/cancelled ⇒ NONE)

SubscriptionEngine::forCurrentTenant() loads the latest subscription (with plan, modules, features) bypassing the tenant scope, then caches the resolved Entitlement in Redis under entitlement:<companyId>:<subscription.updated_at> for 1 hour. Because the cache key includes updated_at, any change to the subscription naturally produces a new key (effective invalidation).

The gate — FeatureAccessService

interface FeatureAccess {
    canAccessModule(string $moduleCode): bool;
    canUseFeature(string $featureCode): bool;     // boolean features
    featureLimit(string $featureCode): ?int;      // null = unlimited
    canAddEmployee(int $count = 1): bool;          // seat check
    canRunPayroll(): bool;                          // module + status
    assert(string $ability, mixed $context = null): void; // throws 403
}
  • Seat math (canAddEmployee): compares active employee count vs seatLimit() = employees.max feature if set, else included_seats + purchasedSeats. Over-limit → 403 SEAT_LIMIT_REACHED.
  • All checks short-circuit to deny when status is expired/suspended/cancelled (accessGranted = false).
  • Employee count is read via a raw guarded query so the service has no hard dependency on the Employee model in early phases.

Enforcement points

  1. Middleware: module:payroll / feature:payroll.bulk on route groups (EnsureModuleAccess/EnsureFeatureAccess).
  2. Service layer: featureAccess->assert(...) before any mutating action.
  3. Frontend (planned): mirrors entitlements from GET /me/entitlements to hide/disable UI — backend remains authoritative.

Lifecycle transitions are now automated
The status enum, gate, and the date-driven transitions are all built. 7. Authentication — JWT access + rotating refresh BUILT

  • Access token: short-lived (default 900s / 15 min), HS256, carries claims sub, company_id, sa (super-admin), typ:"access".
  • Refresh token: long-lived (default 14 days), typ:"refresh" with a jti. A refresh_tokens row stores the hash, device, ip.
  • Rotation: AuthService::refresh() validates, revokes the old token, issues a new pair inside a transaction.
  • Reuse detection: if a refresh token that is already revoked is presented, the entire chain for that user is revoked defensively → forces re-login.
  • Guard: JwtGuard implements the api guard; it reads the Bearer token and rejects non-access tokens.
# config/jwt.php (env-driven)
JWT_SECRET=...            # required (32+ chars)
JWT_ACCESS_TTL=900        # seconds
JWT_REFRESH_TTL=1209600   # 14 days
JWT_ALGO=HS256
Security must-dos for the new team
Set a strong, unique JWT_SECRET per environment (never commit it). Rotate the super-admin password from the seeder default (SUPER_ADMIN_PASSWORD). Always serve over HTTPS so Bearer tokens aren't exposed. MFA, login throttling, and login history are PLANNED (see docs/08-SECURITY.md).

The repo ships a working server block at infra/docker/nginx/default.conf. For a native host, the production version adds TLS:

server {
    listen 80;
    server_name api.yourdomain.com;
    return 301 https://$host$request_uri;        # force HTTPS
}
server {
    listen 443 ssl http2;
    server_name api.yourdomain.com;
    root /var/www/HRM/backend/public;            # Laravel public dir is the web root
    index index.php;
    client_max_body_size 25m;                    # allow file/import uploads

    ssl_certificate     /etc/letsencrypt/live/api.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.yourdomain.com/privkey.pem;

    # Security headers (see docs/08-SECURITY.md)
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location / { try_files $uri $uri/ /index.php?$query_string; }   # pretty URLs → front controller

    location ~ \.php$ {                          # hand .php to PHP-FPM
        fastcgi_pass unix:/run/php/php8.4-fpm.sock;
        fastcgi_index index.php;
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
    }
    location ~ /\.(?!well-known).* { deny all; }  # block dotfiles
}

Request flow: client → Nginx (TLS terminates here) → if the path is a real file it's served directly, otherwise it's rewritten to index.php → forwarded over FastCGI to PHP-FPM → Laravel. For the Docker setup, fastcgi_pass targets app:9000 (the PHP-FPM container) instead of a unix socket. A future Next.js frontend would be reverse-proxied on / with the API kept on /api (or a separate subdomain).

14. Redis configuration

# /etc/redis/redis.conf essentials
bind 127.0.0.1 <private-ip>
requirepass <strong-secret>          # then set REDIS_PASSWORD in .env
maxmemory 1gb
maxmemory-policy allkeys-lru          # evict least-recently-used for the cache role

Redis serves three roles here:

  • Cache (CACHE_STORE=redis) — notably the entitlement cache (1h TTL) so subscription checks are O(1).
  • Queue (QUEUE_CONNECTION=redis) — background jobs.
  • Sessions (SESSION_DRIVER=redis) — though the API is stateless via JWT, session store backs any web/Blade flows.

Performance benefit: in-memory reads (sub-millisecond) keep Postgres free for transactional work; LRU eviction means the cache self-manages under memory pressure.

15. Queue system

Jobs run on a Redis-backed queue. The horizon service in compose runs php artisan queue:work --tries=3 --timeout=120. (Laravel Horizon itself — the dashboard — is referenced in the blueprint but not yet a dependency; plain queue:work is what runs today.)

  • How it works: a job is pushed to Redis; a worker pops it and executes handle(). The HTTP request returns immediately.
  • Failures: with --tries=3, a failing job retries up to 3 times, then lands in the failed_jobs table (the jobs/failed-jobs migrations exist).
  • Retries: php artisan queue:retry all re-queues failed jobs; queue:forget drops one.
# Local
php artisan queue:work --tries=3 --timeout=120

# Production (under Supervisor)
[program:hrms-worker]
command=php /var/www/HRM/backend/artisan queue:work redis --sleep=3 --tries=3 --timeout=120
autostart=true
autorestart=true
user=www-data
numprocs=2
redirect_stderr=true
stdout_logfile=/var/log/hrms-worker.log

18. CI/CD

GitHub Actions (.github/workflows/ci.yml) runs on every push to main and every PR. It spins up real Postgres 16 + Redis 7 service containers and:

  1. Sets up PHP 8.4 with the required extensions.
  2. Caches and installs Composer dependencies.
  3. Copies .env.example and generates an app key.
  4. Lints with Laravel Pint (pint --test).
  5. Migrates against Postgres.
  6. Runs the test suite (php artisan test) — including the tenant-isolation and subscription-gating tests.

Git workflow & branching

  • Work on feature branches (current: feat/foundation-architecture-and-spine); open a PR into main.
  • CI must be green before merge; the tenant-isolation suite is a hard gate.
  • Deployment pipeline (intended): on merge to main, build + scan images, run migrate --force, deploy staging → production with approval. Use expand/contract migrations for zero-downtime.
  • Rollback: redeploy the previous image tag; never destructively reverse data migrations — prefer a forward fix. Keep migrate:rollback for the latest reversible batch only.

  • Database: the module/feature/plan mapping is pure data (seeders); only the recruitment domain tables are new schema.
  • Subscription settings: decide which plans include it (or sell as an add-on via subscription.overrides.modules.add).
  • Permissions: add recruitment.* codes and assign to the right roles.
  • No core changes — modules are additive by design. New models must use BelongsToTenant + HasUuid.

19.3 Change payroll logic BUILT domain

PayrollService::computePayslip (component math)  → the single source of truth
   └─▶ SalaryStructure / SalaryStructureLine / SalaryComponent  → earnings/deductions
        └─▶ PayrollService::process (idempotent, per active employee)
             └─▶ Payslip.breakdown JSON       → exact per-component record
                  └─▶ Payroll reports (summary/register/deductions/tax) [PLANNED]
                       └─▶ Tests: PayrollTest known-input → known-net assertions
  • Service that changes: PayrollService (calculation + the attendance LOP integration in lopDays()).
  • Reports that change: salary register / deduction / tax reports (exports are still PLANNED) must reflect new components.
  • Risk: money math — everything is integer paise; never floats. Extend PayrollTest with fixed-input regression cases.

19.4 Change billing logic BUILT domain

PaymentGateway contract  ← swap/extend adapters (Manual today; Razorpay/Cashfree/PayU next)
   └─▶ GatewayManager (resolves billing.default_gateway, falls back to manual)
        └─▶ WebhookController (verify → persist webhook_events → process)   [idempotent on event_id]
             └─▶ InvoiceService / Payment / SubscriptionService (transaction)
                  └─▶ TaxCalculator (GST) → invoice_lines totals
                       └─▶ Notifications (payment success/failure) [PLANNED]
  • Add a real gateway: implement PaymentGateway, register it in GatewayManager::$adapters, switch via BILLING_DEFAULT_GATEWAY — no business-code change.
  • Webhooks: already verify signature, persist raw for idempotency (unique gateway,event_id), then apply in a transaction. Move processing into a queued job for higher volume.
  • Invoices/subscription calc: InvoiceService handles base + seats + add-ons + GST; extend it for proration on mid-cycle upgrades.

19.5 Add a new role or permission

  • Add the permission code to RolePermissionSeeder::PERMISSIONS and assign it under the relevant role(s); re-run db:seed (idempotent).
  • Apply it on routes via permission:your.code. Side-effect: any route already using it is now enforceable.
  • Risk: forgetting to assign to Company Admin — verify the role matrix after seeding.

21. Monitoring & maintenance

  • Health checks: GET /up (Laravel built-in) behind your LB/uptime monitor.
  • Logs: structured JSON logs shipped to a central store with request-id correlation (intended). Today: stack/single channel to storage/logs.
  • Metrics (planned): Prometheus exporters for app/php-fpm/postgres/redis; Grafana dashboards for business (MRR/ARR) + system health; alerts on queue backlog, error rate, failed payments, expiring subscriptions.
  • Queue monitoring: watch failed_jobs count; add Horizon for throughput/latency dashboards.
  • Database monitoring: pg_stat_statements for slow queries; connection count vs max_connections; bloat/vacuum health.
  • Storage monitoring: disk usage on the DB volume and S3/R2 bucket growth.
  • Security monitoring: failed-login spikes, refresh-token reuse events (already logged via chain-revoke), webhook signature failures.
  • Routine maintenance: patch OS + dependencies monthly; rotate logs; verify backups restore; review CI dependency scans.

22. Backup & recovery

  • Database backups: nightly logical dump plus WAL archiving for point-in-time recovery.
# Nightly logical backup
pg_dump -Fc -U hrms hrms > /backups/hrms-$(date +%F).dump

# Restore
pg_restore -U hrms -d hrms --clean /backups/hrms-2026-06-25.dump

# Docker volume backup (pgdata)
docker run --rm -v hrms_pgdata:/data -v $PWD:/backup alpine \
  tar czf /backup/pgdata-$(date +%F).tgz -C /data .
  • Storage backups: enable versioning on the S3/R2 bucket; replicate cross-region for DR.
  • Server backups: infrastructure-as-code + .env secrets in a secret manager so a host is reproducible; don't rely on snapshots alone.
  • Recovery procedure: provision host → restore DB dump → restore object storage → deploy app at the matching image tag → run migrate → smoke-test /up + login.
  • Disaster recovery: target RPO ≤ 24h (nightly) or ≤ 5 min (WAL); RTO measured by a documented runbook you should rehearse.
  • Business continuity: remember the platform principle — customer data is never destroyed automatically; expiry/suspension only gates access, so reactivation restores everything.
